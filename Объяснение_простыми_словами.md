# Лабораторная №2 — объяснение простыми словами

Во второй лабораторной программа **считает, сколько раз каждое слово встретилось в текстовых файлах**, и сравнивает разные способы работы нескольких потоков с общими данными.

В первой лабораторной каждый поток независимо считал свою часть интеграла. Здесь появляется новая проблема: **несколько потоков могут одновременно попытаться изменить счётчик одного и того же слова**.

Из-за этого программа может работать быстро, но давать неправильный ответ. Именно это лабораторная и исследует.

## 1. Что должна делать программа

Допустим, в файле написано:

```text
Кот собака кот
СОБАКА кот!
```

Программа должна привести слова к единому виду и получить:

```text
кот → 3
собака → 2
```

Для хранения используется **словарь**, или `Map`:

```java
Map<String, Long>
```

Это структура вида `ключ → значение`. В нашем случае `String` — слово, а `Long` — количество его появлений.

```java
map.put("кот", 3L);
```

означает «записать для слова кот количество 3».

```java
map.get("кот");
```

означает «получить количество для слова кот».

## 2. Из каких частей состоит проект

Код разделён на несколько файлов, чтобы разные обязанности не смешивались.

| Файл | За что отвечает |
|---|---|
| `TestDataGenerator.java` | Создаёт текстовые файлы и правильный ответ |
| `TextFiles.java` | Находит файлы, читает и нормализует слова |
| `WordAnalyzer.java` | Задаёт общий способ вызова анализаторов |
| `Analyzers.java` | Содержит семь вариантов подсчёта |
| `Benchmark.java` | Измеряет время и проверяет результаты |
| `Main.java` | Запускает эксперимент с выбранными настройками |

Выполнение выглядит так:

```text
Генератор создаёт тексты и эталон
                  ↓
Main читает настройки
                  ↓
Benchmark запускает анализаторы
                  ↓
Каждый анализатор считает слова
                  ↓
Benchmark проверяет ответ и сохраняет измерения
```

## 3. Генератор: откуда берутся тексты

Для экспериментов не нужно вручную писать тысячи строк. Их создаёт `TestDataGenerator`.

Он формирует словарь:

```text
word0000
word0001
word0002
...
word0499
```

Каждому слову назначается вероятность появления. Одни слова встречаются чаще, другие реже.

Далее генератор многократно выбирает случайное слово и записывает его в файл. При этом может изменить регистр или добавить пунктуацию:

```text
word0001 WORD0024, Word0001! word0380;
```

Это нужно, чтобы проверить не только подсчёт, но и обработку текста.

В генераторе есть:

```java
expected[index]++;
```

`expected` — массив правильных счётчиков. Когда генератор выбирает слово, он сразу увеличивает его счётчик.

**Правильный ответ считается в момент создания текста**, до добавления пунктуации и изменения регистра.

После генерации появляются:

| Файл | Содержимое |
|---|---|
| `text-001.txt`, `text-002.txt` и другие | Тексты для обработки |
| `expected-statistics.txt` | Точное количество каждого слова |
| `distribution.txt` | Вероятности появления слов |
| `generation.properties` | Параметры генерации и `seed` |

`seed` — начальное значение генератора случайных чисел. С тем же `seed` и теми же параметрами можно повторно получить те же тексты.

Все анализаторы внутри одного эксперимента получают **одни и те же файлы**.

## 4. Как программа читает и очищает слова

Этим занимается `TextFiles.java`.

Сначала метод `list` получает список текстовых файлов. Он исключает `expected-statistics.txt` и `distribution.txt`. Их нельзя считать обычными входными текстами: это служебные данные.

Затем метод `read` читает каждый файл построчно:

```java
while ((line = reader.readLine()) != null)
```

Это означает: «читать следующую строку, пока строки не закончатся». Весь корпус не загружается в память сразу.

Регистр приводится к нижнему:

```java
line.toLowerCase(Locale.ROOT)
```

Поэтому `WORD0001`, `Word0001` и `word0001` превращаются в одинаковое `word0001`.

Слова выделяются шаблоном:

```java
"[\\p{L}\\p{N}]+"
```

Он означает «последовательность букв и цифр». Например, `Word0001, WORD0002!` после обработки даёт слова `word0001` и `word0002`.

Цифры сохраняются, пунктуация служит разделителем.

## 5. Зачем нужен WordAnalyzer

В нём описан общий метод:

```java
Map<String, Long> analyze(Path directory, int threads)
        throws Exception;
```

Он получает каталог с текстами `directory` и количество потоков `threads`. Возвращает готовый словарь частот.

Разные анализаторы используют разные способы подсчёта, но вызываются одинаково. Поэтому `Benchmark` может измерять их одним и тем же способом.

Это похоже на несколько калькуляторов с одной кнопкой «посчитать»: внутреннее устройство разное, а результат ожидается одинаковый.

## 6. Последовательный вариант

Первый анализатор — `SequentialAnalyzer`. Он создаёт обычный словарь:

```java
Map<String, Integer> map = new HashMap<>();
```

И для каждого слова выполняет:

```java
map.put(w, map.getOrDefault(w, 0) + 1);
```

`map.getOrDefault(w, 0)` означает: получить текущий счётчик слова `w`; если слова ещё нет, взять 0. Затем `+ 1` увеличивает счётчик, а `map.put(...)` сохраняет новое значение.

```text
Первое появление:  0 + 1 → 1
Второе появление:  1 + 1 → 2
Третье появление:  2 + 1 → 3
```

Всё выполняется одним потоком, поэтому никто не меняет счётчик между чтением и записью. Этот вариант корректен.

В конце счётчики преобразуются из `Integer` в `Long`, чтобы все анализаторы возвращали одинаковый тип результата.

## 7. Как файлы распределяются между потоками

В `Analyzers.java` есть общий метод `parallel`. Он создаёт пул:

```java
ExecutorService pool =
        Executors.newFixedThreadPool(threads);
```

**Пул потоков** — группа работников, которым можно выдавать задачи.

В нашей программе каждому работнику назначается группа файлов:

```java
for (int i = t; i < files.size(); i += threads)
```

Пусть файлов восемь, а потоков два:

```text
Работник 0: файлы 0, 2, 4, 6
Работник 1: файлы 1, 3, 5, 7
```

При четырёх потоках:

```text
Работник 0: файлы 0, 4
Работник 1: файлы 1, 5
Работник 2: файлы 2, 6
Работник 3: файлы 3, 7
```

Общий объём текста остаётся одинаковым.

Задачи отправляются в пул через `pool.submit(...)`. Этот метод возвращает `Future` — объект, через который можно дождаться результата задачи:

```java
future.get();
```

Ещё используется `CountDownLatch`. Здесь он работает как общий сигнал старта: задачи сначала ждут, затем получают разрешение начать обработку.

## 8. Главная проблема: потеря обновления

Представим, что слово кот уже встретилось десять раз. Два потока одновременно обрабатывают ещё по одному появлению. Правильный результат — 12.

Но выражение:

```java
map.put(word, map.getOrDefault(word, 0) + 1);
```

состоит из отдельных действий: `прочитать → прибавить → записать`. Они могут перемешаться:

| Шаг | Поток A | Поток B |
|---|---|---|
| 1 | Прочитал 10 | |
| 2 | | Прочитал 10 |
| 3 | Вычислил 11 | |
| 4 | | Вычислил 11 |
| 5 | Записал 11 | |
| 6 | | Записал 11 |

Получили 11, хотя нужно 12. Это называется **потерей обновления — lost update**. Слово было в тексте, но одно из увеличений счётчика потерялось.

## 9. Общий HashMap

Вариант `hashmap` даёт всем потокам один обычный `HashMap`.

Проблемы здесь две:

- возможна потеря обновлений;
- сама внутренняя структура HashMap не предназначена для одновременных изменений несколькими потоками без защиты.

Поэтому такой вариант намеренно включён как ошибочный пример. Он иногда может выдать правильный ответ. Это зависит от того, как совпали действия потоков. **Удачный запуск не доказывает безопасность.**

## 10. synchronizedMap

Следующий вариант создаёт:

```java
Collections.synchronizedMap(new HashMap<>());
```

Этот словарь защищает свои отдельные методы общей блокировкой. Условно: пока один поток выполняет защищённый вызов, другой ждёт.

Но мы всё ещё выполняем `map.getOrDefault(...)` и `map.put(...)` как **два отдельных вызова**. Между ними другой поток может изменить значение. Поэтому потеря обновлений сохраняется.

Чтобы сделать именно такую составную операцию корректной, нужно защитить целиком чтение, увеличение и запись одной общей блокировкой. В нашей лабораторной этот вариант оставлен наивным, чтобы показать проблему.

## 11. ConcurrentHashMap с get и put

Вариант `concurrent-get-put` использует:

```java
new ConcurrentHashMap<>();
```

Это словарь, рассчитанный на конкурентный доступ. Он позволяет потокам безопасно работать со структурой словаря. Но последовательность «прочитать значение, прибавить один, записать значение» автоматически не становится одной операцией.

Поэтому такой код тоже может терять увеличения:

```java
map.put(word, map.getOrDefault(word, 0) + 1);
```

Главная мысль: **потокобезопасная структура и потокобезопасный алгоритм — разные вещи.**

## 12. Корректный вариант: ConcurrentHashMap.merge

Здесь обновление выглядит так:

```java
map.merge(word, 1, Integer::sum);
```

Если слова нет — записать 1. Если есть — прибавить 1 к текущему счётчику. `Integer::sum` — ссылка на действие сложения двух целых чисел.

Для ConcurrentHashMap это обновление выполняется **атомарно для ключа**. Атомарность означает, что другой поток не может вклиниться между чтением старого значения и записью нового так, чтобы потерять увеличение.

Поэтому два появления корректно превращают 10 в 12.

## 13. ConcurrentHashMap с LongAdder

Этот анализатор хранит:

```java
ConcurrentHashMap<String, LongAdder>
```

Значение здесь — специальный конкурентный счётчик. Обновление:

```java
map.computeIfAbsent(word, key -> new LongAdder())
   .increment();
```

`computeIfAbsent(...)` означает: получить счётчик слова, а если его ещё нет — создать. `increment()` увеличивает счётчик на один.

LongAdder может распределять конкурирующие увеличения между внутренними ячейками, уменьшая борьбу потоков за один счётчик.

После окончания всех работников `adder.sum()` возвращает итоговую сумму.

**В нашей программе sum() вызывается после завершения потоков.** Во время продолжающихся обновлений он не является атомарным снимком всех изменений.

Этот вариант корректен, но не обязан быть самым быстрым на любом корпусе: у него тоже есть свои расходы.

## 14. Локальные словари

Вариант `local-maps` вообще убирает общий словарь из основного подсчёта. У каждого работника собственный HashMap:

```text
Работник 1 → свой словарь
Работник 2 → свой словарь
Работник 3 → свой словарь
```

Например:

```text
Словарь 1: кот → 5
Словарь 2: кот → 7
Словарь 3: кот → 3
```

После завершения работников главный поток объединяет результаты: `кот → 15`.

В коде:

```java
result.merge(w, count.longValue(), Long::sum);
```

Объединение выполняет один поток, поэтому обычного HashMap для итогового словаря достаточно.

Преимущества: работники не конкурируют за общий счётчик, во время основного подсчёта не нужна защита словаря. Расходы: нужно хранить несколько словарей и требуется финальное объединение.

## 15. Как Benchmark проверяет правильность

До измерений загружается `expected-statistics.txt`.

После каждого запуска программа получает фактический словарь и сравнивает его с эталоном:

```java
actual.equals(expected)
```

Для словарей это проверяет одинаковый набор ключей и одинаковые значения.

Дополнительно записываются число слов с несовпадающими счётчиками, общее количество посчитанных слов и ошибка выполнения, если она произошла.

Например, если ожидается 512000 слов, а получилось 511832, часть увеличений потерялась. Но одной общей суммы недостаточно: программа проверяет **каждое слово**, потому что ошибки отдельных счётчиков могут взаимно компенсироваться.

## 16. Как измеряется время

Как и в первой лабораторной, используются прогревы и основные измерения. Для каждого варианта и количества потоков: 2 прогрева и 5 основных запусков.

Время определяется через:

```java
long start = System.nanoTime();
actual = analyzer.analyze(directory, threads);
double seconds = (System.nanoTime() - start) / 1e9;
```

В замер входят получение списка файлов, чтение текста, нормализация, подсчёт, организация потоков и объединение результатов.

Проверка правильности и сохранение таблиц выполняются после остановки таймера.

Из пяти основных времён берётся **медиана** — центральное значение после сортировки. Дополнительно сохраняется минимум.

## 17. Ускорение и эффективность

База здесь — **последовательный анализатор** на том же корпусе.

```text
Ускорение = время последовательной версии / время выбранного варианта
```

Например:

```text
Последовательно: 0,20 секунды
4 потока:         0,08 секунды

Ускорение = 0,20 / 0,08 = 2,5 раза
```

Эффективность:

```text
2,5 / 4 × 100% = 62,5%
```

Получили 62,5% от идеального ускорения в четыре раза.

Но сначала нужно проверить правильность. **Быстрый алгоритм, потерявший часть слов, нельзя считать хорошим решением задачи.**

## 18. Как запускает всё Main

Main читает параметры, например:

```text
--data=generated-data/small
--variant=long-adder
--threads=1,2,4,8
--warmups=2
--runs=5
```

| Параметр | Что выбрать |
|---|---|
| `--data` | Каталог входных текстов |
| `--variant` | Способ подсчёта |
| `--threads` | Количества потоков |
| `--warmups` | Количество прогревов |
| `--runs` | Количество основных замеров |
| `--out` | Каталог результатов |

Затем Main передаёт настройки в `Benchmark.run(...)`.

Если выбран один параллельный вариант, программа всё равно сначала измеряет последовательную версию, чтобы получить базу для ускорения.

## 19. Какие результаты получились

Мы проверили три корпуса:

| Корпус | Файлов | Всего слов |
|---|---:|---:|
| Малый | 64 | 32 000 |
| Средний | 64 | 128 000 |
| Большой | 64 | 512 000 |

В каждом случае проверялись количества потоков от 1 до 64.

Результат по правильности:

- последовательный вариант прошёл проверки;
- `concurrent-merge`, `long-adder` и `local-maps` совпали с эталоном во всех запусках;
- общий HashMap, наивный synchronizedMap и ConcurrentHashMap с get/put давали ошибки при многопоточном подсчёте.

На большом корпусе среди корректных параллельных вариантов минимальное измеренное время показал **concurrent-merge с 16 потоками** — около 0,071 секунды. Последовательная версия заняла около 0,217 секунды.

Это ускорение примерно в **3,05 раза**.

Такие результаты относятся к этой серии измерений. На них влияют процессор, файловый кэш, оптимизация Java и фоновая нагрузка.

## 20. Что запомнить для защиты

Можно объяснить работу так:

> Программа подсчитывает частоты слов в текстовых файлах. Генератор создаёт корпус и независимый эталон. Файлы распределяются между потоками, а разные реализации используют разные способы обновления счётчиков. Общие словари с отдельными get и put могут терять обновления. Для корректного подсчёта используются ConcurrentHashMap.merge, LongAdder или локальные словари с последующим объединением. Каждый запуск проверяется по эталону, после чего сравниваются медианное время, ускорение и эффективность.

Самое важное различие между двумя лабораторными: **в первой мы в основном исследовали скорость, а во второй — ещё и то, как сохранить правильный результат при одновременной работе потоков.**
